## 0. Технология: что предлагаю вместо «React + Express»

Твой вариант верен на 90%, я меняю 4 вещи:

| Слой | Твой вариант | Предлагаю | Почему |
|---|---|---|---|
| UI | React | **React 19 + Vite + TypeScript** | Vite вместо CRA/CJS — мгновенный dev-сервер, TS окупается сразу: Brief, промпты и манифест артефактов должны иметь один тип на фронте и бэке |
| Бэк | Express | **Fastify 5** или Express 5 (обёртка ~150 строк) | Разница не в скорости, а в том, что Fastify отдаёт SSE/streaming и валидацию по схеме из коробки |
| Модельный слой | «разные модели» | **OpenAI-compatible adapter** (`/v1/chat/completions`) + реестр моделей в конфиге | У тебя уже есть `OPENROUTER_API_KEY`, `LITELLM_KEY`, `ZAI_API_KEY` — все три говорят по OpenAI-совместимому протоколу. Никаких SDK от вендоров |
| Изображения | «генерация изображений» | **CLI `imagening` как раннер** (spawn) | Already signed-in, очередь/лейн/модели/формы уже решены, не нужен свой HTTP-клиент и ключ в коде |
| Хранилище | ? | **Файловая система + JSON/JSONL, без БД** | Один проект = одна папка. SQLite добавит миграции ради того, что делает `ls` |
| Тесты | ? | **Playwright-core** (chromium из кэша) | Уже скачан, 0 скачиваний, даёт скриншот + console errors + DOM-данные в одном прогоне |
| Запуск | ? | `npm run dev` = concurrently(vite, tsx watch server) → один URL `http://localhost:5173`, прокси на `/api` | «Локальный браузерный» = ты видишь только браузер, порт сайдкара не заметен |

Альтернатива, если хочешь **буквально один бинарник без браузера**: Tauri (Rust). Цена: Rust-тулчейн, медленнее итерации, сложнее скармливать скриншоты модели. Не советую для MVP.
Electron — тяжелее Tauri, тот же минус. **Чистый браузер + File System Access API** — невозможно запустить `imagening` и Chrome → отпадает.

Предлагаемая структура:

```
~/Builder/
  package.json          # workspace root (npm workspaces)
  packages/
    shared/             # TS-типы: Brief, Manifest, OrchEvent  — один источник правды
    server/             # Fastify: /api/*, orchestrator, runners/ (model, imagening, playwright)
    web/                # React: форма Brief → мастер промптов → монитор прогонов → превью
  prompts/              # *.md.jte шаблоны (versioned!) — НЕ внутри кода
  projects/             # один прогон = одна папка (см. §10)
  settings.json         # модели, лимиты, ключи-имена-env
```

## 4. Мастер-промпт (тут главное расхождение с твоей формулировкой)

**4.1 Признаёшь, что «Brief JSON → один master-промпт → модель пишет код» не даёт параллельных картинок и текстов?** Предлагаю: Brief → **prompt program** из 5 шаблонов (`plan`, `copy`, `image-prompts`, `page-code`, `fix`), все из `prompts/*.md.jte`, все версионируемые, и у каждого — свой контракт вывода.
→ дефолт: да.

**4.2 Порядок: план прежде кода.** Сначала модель выдаёт `site-plan.json` (секции, заголовки, SLUG-имена картинок, палитра), он валидируется и является **единственным источником имён файлов** для параллельных веток. Так `page-code` и `image gen` не разъезжаются по именам.
→ дефолт: да, план обязателен и редактируется вручную в UI перед прогоном.

**4.3 Формат вывода кода:** (а) один HTML-файл целиком; (б) HTML + CSS + JS отдельными файлами; (в) пачка файлов через «file fence» блок (`=== file: assets/app.js ===`); (г) вызов функции-записи.
→ дефолт: **(в)** для многосегментных, с парсером, который не принимает ничего вне фенсов. Для variants по умолчанию (а).

**4.4 Что модель не имеет права:** менять имена файлов из плана, использовать внешние图片-URL, писать JS-фреймворк, оставлять `href=""`. Правила-запреты вынесем в `constraints.hardRules` и будем **дрочить валидатором**, а не просьбой в промпте. Согласен?
→ дефолт: да.

**4.5 Температуры/длины** — в реестр ролей или в Brief?
→ дефолт: в реестр ролей (это техническая настройка, не креативная).

**4.6 Кэш промптов:** одинаковый Brief + одинаковый seed + неизменный шаблон ⇒ не дёргать модель повторно. Нужен?
→ дефолт: да, кэш по хэшу (promptVersion, role, model, input, seed) в `.cache/prompts/`. Это экономит и деньги, и нервы при отладке оркестратора.

## 7. Оркестратор (твоя «операций больше, чем кодинг»)

Модель: **DAG из задач + event log + чекпоинты**, а не «функция с await-ами». Узлы:

```
brief → expand → plan → validate(plan) ─┬→ copy ─┐
                                        ├→ image-prompts → images[4] ─┤
                                        └→ (pallette/fonts)           ├→ assemble → serve → test ─┐
                                                                                                   ├→ fix loop (≤N) → export
                                                                                                   ┘
```

**7.1 Что для тебя обязательнее: восстановимость после падения или простота отладки?**
→ дефолт: восстановимость. Каждая задача пишет результат в `projects/<id>/artifacts/`, при рестарте прогона готовые задачи со валидным артефактом пропускаются.

**7.2 Прогресс в UI:** SSE или WebSocket?
→ дефолт: **SSE** — однонаправленный поток событий, нет reconnect-протокола, работает из коробки.

**7.3 Приостановка на ручном подтверждении** (plan, тексты, отобрать картинки) — нужна или «нажал старт и ушёл»?
→ дефолт: `gates: [plan, none]` — шлюз по умолчанию один, после плана; остальные gates настраиваются.

**7.4 Отмена:** убиваем только свой `node`-дочерний процесс, или просим Imagening `cancel` тоже?
→ дефолт: отменяем своё, у Imagening зовём `imagening cancel <id>`.

**7.5 Ресурсы машины (4 ядра / 7.8 ГБ):** сколько прогонов и Chrome одновременно?
→ дефолт: 1 прогон, 1 Chromium, 4 картинки, 1 code-модель. Жёстко в `settings.json`, без авто-эвристики.

**7.6 Логи:** один `run.jsonl` на прогон со всеми событиями (prompt hash, usage, duration, raw). Годится как единственный формат?
→ дефолт: да + `report.md` для человека.

## 8. Тестирование и самоисправление (тут рождается качество)

**8.1 Что проверяем** (мой список, отметь/дополни):
1. файл собрался и открылся, нет 404 на ассеты;
2. консоль без ошибок, нет неопределённых глобалов;
3. **визуальные сдвиги**: ни один `.clip`/секция не налегает, нет `overflow`, нет пустых блоков;
4. контентные анкоры: price/cta/phone на месте;
5. контраст текста (WCAG AA на bg/accent);
6. битые href (стоят ли заглушки там, где нечего);
7. скролл-тест 375/768/1280 — по скриншоту;
8. Lighthouse-лайт: LCP/CLS (у тебя нет Docker, значит `lighthouse` через тот же Chrome или вообще v2);
9. `impeccable detect --json` как отдельный тест-раннер (уже глобален);
10. red-shade не повторил прошлый проект серии.

→ дефолт: 1–7 + 9 + 10 в MVP, 8 — v2.

**8.2 Кто смотрит скриншоты:** vision-модель с чек-листом и правом вердикта, или только детекторы без зрения?
→ дефолт: vision-пасс обязателен (дешёвая vision-модель), он же источник правки.

**8.3 Fix loop:** максимум раундов и что именно шлём модели (весь HTML + описание дефекта / только CSS-патч / diff)?
→ дефолт: `maxFixRounds = 2`, шлём **только CSS/HTML-фрагмент** + точное описание дефекта и селектор. Просьба «переписать всё заново» — источник регрессий.

**8.4 Стоп-условие «достаточно хорошо»:** все критичные проверки зелёные? балл выше порога? просто 2 раунда и сдаёмся?
→ дефолт: критичные (1,2,3,4) зелёные → готово; иначе после 2 раундов — статус `needs_human` с отчётом, а не тихий мусор.

**8.5 Нужны ли регрессионные тесты самого генератора** (зафиксированный Brief → золотой `site-plan.json` + палиндом-тест промпт-парсера)?
→ дефолт: да, vitest + 2 фикстуры; это единственная защита от того, что правка шаблона промпта молча всё сломает.

- **11.2 Конфиг**: `~/Builder/settings.json` (модели, лимиты) +Brief в проекте. Никаких `.env` на проект? → дефолт: `.env` один на корень.
- **11.3 Обновляемость промптов без релиза**: да, шаблоны на диске, хэш входит в кэш.
- **11.4 Безопасность**: сайдкар слушает 127.0.0.1, никаких внешних хостов, кроме model API и Imagening. Подтверди (иначе spawn-ах с пользовательскими аргументами надо экранировать).
- **11.5 Что деградировать при отсутствии**: Chrome → пропускаем тесты с явным warning; Imagening не залогинен → прогон стартует без картинок; ключ модели нет → старт формы с ошибкой на кнопке Run.

## 13. Раунд 11 — хотелки юзера (2026-10-30, после зелёного смоука)

**13.1 Индикатор интернета в хедере.** Причина «почему модель остановила генерацию» должна

транспорт-ретраи → 500-шторм → пауза; монитор прогона показывает последнюю `task.error`
крупно. Индикатор лишь объясняет причину.

**13.2 Нет image-модели — основная модель не стопорится.**
→ принято: картинка никогда не валит прогон (уже так: `tasks.image` ловит любую ошибку и
кладёт SVG-плейсхолдер в палитре по slug). Режимы `none`/`manual` работают с первого дня.

**13.6 Раунд 12 — только тёмная тема, единое полотно, палочки сигнала (2026-10-30).**

`hero-code.dark.svg` тоже больше нет). White/Black остаётся только режимом лендинга
(что генерим), витрину оно не перекрашивает; вместо свитчера — метка в хедере.
→ Hero — **единое полотно на всю ширину**, а не «три полосы»: один поток токенов,
заворачиваемый по полной ширине (146 знаков на строку), номер строки один слева,
разрывов между «колонками» нет. Прежние три колонки давали визуальные полосы.
→ Индикатор связи — **10 палочек** (деления сигнала) в хедере: хороший сигнал — все
зелёные; средний — половина жёлтых; плохой — две красные (моргает). Уровень =
доля отвечающих подключений + штраф за долгий ответ; клик = перепроверка.

**Пойманные ловушки (не повторять):**
- `text.slice(fit.length)` вместо `text.slice(fit)` при переносе токена по ширине:
  `slice(undefined)` = вся строка → бесконечный `while` → OOM через 2 ГБ и 4 минуты.
  Симптом обманчив: «зависает генератор», а не «ошибка».
- Блоки ленты обязаны иметь **разные y** (`yOff`), иначе рисуются на одних строках
  и превращаются в кашу вместо прокрутки.
- vite после серии HMR оставляет пустой `<style>` (страница «раздевается»);
  лечится перезапуском dev-сервера, не кодом.

⚠ Открыто (ждёт юзера): `pageCount` 4–6 означает многостраничник (SPEC §5: about/
contact/ services/ policy/ terms/ thanks/ + site.config.json). Делать ли его в этом
итерации или оставить 1 страницу и перенести многостраничник в пост-шаг?

**13.7 Раунд 13 — палочки, перспектива, каретка (2026-11-02).**
→ Палочки индикатора **одной высоты** (14px): растущие по номеру читались как
гистограмма/график, а не как деления уровня сигнала.
→ Полотно кода — в **лёгкой перспективе**: `perspective: 1400px` + `rotateX(7deg)
scale(1.04)` на `.hero-art svg` (CSS, не SVG-матрица — в SVG-матрице skew ломал
номера строк как «колонки»). Из-за поворота у `.hero-art` вертикальные отступы
`inset: -4% … -18% …`: без них по нижнему/верхнему краю были бы щели.
→ Скорость ленты **замедлена вдвое**: 147s → **296s** на цикл (это и есть «0.35×»).
→ **Моргающего курсора нет**: `<rect class="caret">` и его keyframes удалены из
генератора — полотно листается без него.

Ловушка рядом: в `@keyframes` для SVG-группы смещение живёт только в
`transform: translateY(-Npx)`; если при переносе строчки потерять `transform:`
(останется голое `translateY(-Npx) { }`) — анимация молча не работает, лента стоит,
и по одному скриншоту это не отличить от «просто очень медленно». Проверять
`getComputedStyle(tape).animation`, а не только картинку.

**13.8 Раунд 14 — перспектива полотна: не «вверху», а слева и по диагонали (2026-11-02).**
→ `rotateX(24deg)` дал «лист отклонён вверх»: дальним был верхний край, что читалось
как крышка, а не как экран. Теперь наклон **по диагонали**, но мягкий: `rotateY(-9deg)
rotateX(3deg) scale(1.04)`, `perspective: 1400px` с `perspective-origin: 0% 20%` и
`transform-origin: 70% 45%` — левый край дальний (код там чуть мельче и уходит
за сайдбар), правый ближе к зрителю.
→ Перебор тоже дефект: `-18deg / rotateX(6deg) / perspective 900` давало «триполосый
экран из кинопиратства», номера строк слева разъезжались. Ориентир — пока полотно
ещё читается как код, а не как афиша: `~9deg`, `perspective ≥ 1200px`.
→ Запас `inset` сменился на `-14% -14% -18% 6%`: слева отступ **положительный** —
полотно начинается правее сайдбара, иначе дальний левый край с номерами строк
оказывался под ним; справа/сверху/снизу, наоборот, отрицательные, чтобы поворот
не оставил щелей.
→ Проверка не только скриншотом: `getComputedStyle(svg).transform` должен быть
`matrix3d(...)` с ненулевыми `0.3x` в первой строке — иначе перспектива не применилась
(например, `transform` съел другой селектор).

**13.9 Раунд 15 — перспективу убрали совсем, линейки едут с кодом (2026-11-02).**
→ Три шага мягчения (24° → 9° → 3°) не helped: любой наклон спорит с нумерацией строк.
Итог: **перспективы нет** — `.hero-art { inset: 0 }`, у svg ни transform, ни
perspective; полотно плоское и начинается от края hero, то есть от сайдбара
(возврат к инлайновому gutters-решению из генератора, не к CSS-сдвигу).
→ Скорость ленты ещё вдвое: **296s → 592s** на цикл.
→ Строки-линейки были статичным `<rect>` под лентой — при едущем коде это читалось
как разсинхрон. Перенёс их **внутрь `.tape`** (высота `H + shift`, чтобы нижний край
не поднимался выше clip при полном подъёме). Прозрачность кода 0.30 переехала на
вложенную группу: иначе она applying к обеим, и линейки гасли вместе с кодом.
→ Проверяется так: `tape.querySelector("rect[fill^='url']")` есть, и `getBoundingClientRect().y`
ленты меняется со временем — иначе «едет код, стоят полосы» не видно по скриншоту.

black — графитовая, таб показывает серию, а не подсветку.

Ловушки раунда: `hidden={...}` на элементе с `display:flex` из CSS не прячет его
(атрибут бьётся правилом) — нужен условный рендер; placeholder с `&#10;` React
показывает буквально, переносы в плейсхолдере не работают.

`runs-panel.tsx` в сайдбаре: состояние, число картинок/дефектов, дата, ссылка на
`dist/index.html`, автообновление раз 10 с + событие `RUNS_REFRESH` из бриф-формы.
→ Причина сбоя тянется из `run.jsonl` (последняя `task.error`), состояние — из
`run.state`: при сбое на планировании `manifest.json` не успевает создаться, и без
журнала прогон показывался «черновиком» вместо «сбоя».
→ **Повторный запуск того же white/black** падал с «проект уже есть» (409) и прогон не
стартовал: второй клик теперь перезаписывает `brief.json` (`?force=1`).
→ **Скролл сайдбара**: раскрытая форма подключения делала сайдбар длиннее экрана, и
скролл ловила вся страница. Теперь `overflow-y: auto` + `overscroll-behavior: contain`
на `.sidebar` (в мобильной раскладке — `overflow: visible`), у `.runs-list` снят
вложенный `max-height` — один скролл, а не два.

⚠ Открыто: `settings.json` раздулся до 30 КБ из-за 452 записанных моделей; если это

## Что я считаю рисками (не вопросы, а предупреждения)

1. **Имена файлов** — расхождение между тем, что просит HTML, и тем, что положила генерация. Лечится только `site-plan.json` как контрактом + валидатором (п. 4.2/4.4).
2. **Полнота HTML от большой модели**: обрывы на середине, «остальное по аналогии», `<!-- TODO -->`. Лечится фенсами + парсером + приёмкой по числу закрытых тегов и числу секций.
3. **Регрессии в fix loop**: правка «поправь отступ» часто ломаетhero. Лечится diff-только + скриншот-диффом до/после.
4. **Память**: Chromium + Node + 4 картинки на 7.8 ГБ. Один Chrome, всегда с `--disable-dev-shm-usage`, закрывать явно (у тебя уже был случай с обрезанным файлом после таймаута — тут та же ловушка).
5. **Промпты в коде**: как только шаблоны окажутся в строках внутри `.ts`, перестанешь их править и качество встанет. Поэтому `prompts/` отдельной папкой с версии.
