Порядок — как приходило. Решения помечены ✅, открытые — ❓.

## Раунд 1 — база
- Интерактивный браузерный конструктор сайтов/лендингов, всё локально, без внешних серверов.
- Поля формы → Brief JSON → подстановка в мастер-промпт → модель пишет код.
- Оркестратор обязателен: код + параллельные картинки + продающие тексты + тестирование.
- Технологии предположительно React + Express; окончательный выбор — после гриля.

## Раунд 3 — модели (левый/правый сайдбар)
- ✅ Правый сайдбар: список **активных моделей** + счётчик лимита рядом; безлимит — иконка ∞.
- ✅ Возможность подключить **свою модель по любому API** — генератор отдаётся коллеге,
  тот вписывает свои ключи/эндпоинты и работает.
- ✅ Не ограничиваться 1–2 моделями: реестр произвольной длины, гибкая настройка.

### Модель = «подключение» (connection), а не «модель»
Сущность в реестре:
```jsonc
{ id, name, kind: llm | image | tts, baseUrl, keyEnv | keyLocal,
  models: [...], protocol: openai | anthropic | custom,
  roles: { code?, copy?, vision? }, limit: {...}, enabled }
```
- Ролей фиксированный набор: `code`, `copy`, `vision`, `image` (imagening — тоже подключение).
- Одна модель может занимать несколько ролей; у роли может быть **цепочка fallback**.
- Кнопка «Проверить» на подключении: пинг эндпоинта (1 токеновый запрос) + латентность.

### Счётчик лимита — три источника честности (по убыванию)
1. **API провайдера**: OpenRouter `/api/v1/credits`, LiteLLM `/key/info`,
   ElevenLabs `/v1/user/subscription` — точный остаток.
2. **Локальный подсчёт** из `run.jsonl`: запросы/токены/символы за период — помечать как «оценка».
3. **Вручную**: безлимит → иконка ∞; неизвестно → «?» вместо вранья.
- ❓ Порог предупреждения (например, жёлтый при <10%, красный при 0 и авто-исключение роли).

### Переносимость к коллеге
- Всё в двух файлах: `settings.json` (подключения, роли, лимиты) + `.env` (ключи).
- Ключи можно вносить и в UI — хранятся локально, никуда не уходят (127.0.0.1).
- ❓ Экспорт/импорт конфига одной кнопкой (с ключами / без ключей)?

## Раунд 4 — передача коллеге и задел под сервер
- ✅ Передача = максимально просто: скачал/распаковал → одна команда → браузер сам открылся.
- ✅ Акцент 100% на локалку; сервер — «если понадобится», не усложняем сейчас.

### Что делаю ради передачи (дёшево сейчас, дорого потом)
- `npm install && npm start` → стартует сайдкар + открывает `localhost:5173`. Один скрипт,
  ноль ручных шагов, ноль «прочитай README и найди порт».
- Первый запуск = **мастер из 3 шагов** прямо в браузере: ключ модели → проверка соединения
  → рабочая папка проектов. Не форма на 60 полей, а три поля.
- **Авто-детект недостающего**: нет ключа/нет Chrome/`imagening` не залогинен → конструктор
  работает, а недостающая функция показана серой плашкой с причиной, а не падает ошибкой.
- `doctor`-команда (`npm run doctor`) для «у коллеги не работает»: честный список
  (Node ≥20, ключи по именам env, Chrome в кэше, imagening логин, свободен ли порт) + что чинить.
- Порты: брать из `settings.json`, при занятом — следующий свободный + открыть правильный URL,
  а не тупить с EADDRINUSE.
- Никаких нативных зависимостей, требующих компиляции, — иначе у коллеги `npm install`
  падает на node-gyp. Это ограничение принимаю заранее.

### Дешёвый задел под будущий сервер (не серверная архитектура, а отсутствие блокирующих решений)
1. **Фронт не знает про файловую систему**: все операции через один слой вызовов к сайдкару
   (`api.projects.list()`, `api.run.start()`…), а не `fetch` с URL по всему коду.
   Переезд = поменять транспорт, а не переписать UI.
2. **Путь к проектам — одна настройка** (`projectsRoot`), а не «рядом с кодом».
3. **Никакого состояния генератора в памяти процесса без записи на диск**: прогон живёт
   в папке проекта + `run.jsonl`, поэтому серверный вариант — это «тот же сайдкар, но
   на другой машине», без переписывания оркестратора.
4. **Сессия/один пользователь сейчас, но вызовы уже несут `projectId`** — чтобы мультипользователь
   не потребовал переписывать «куда писать».
5. Не делаю (дорого и не нужно пока): аутентификацию, Docker, многопользовательские квоты,
   object storage, очередь задач вне процесса.

❓ Если сервер всё же понадобится — сценарий другой: «удалённая машина с GPU/дорогой моделью,
UI локально» или «коллега заходит в мой генератор по ссылке из браузера»? Второй стоит дороже
(нужны логин и изоляция прогонов), первый почти бесплатен при заделе выше.

## Раунд 7 — `imagening` вне списка; выбор моделей = два селекта
- ✅ `imagening` — **наш** генератор картинок, в реестр моделей генератора **не входит**.
  Т.е. генератор оперирует только тем, что подключено как API-подключение.
  (❗ consequence: до появления kie.ai-ключа картинок нет вообще — см. «Риски».)
- ✅ UI выбора: **два селекта** — «Модель для кода/текста» и «Модель для графики».

### Как устроены оба селекта (чтобы «гибко» не превратилось в 12 полей)
Каскад из двух уровней, потому что у подключения много моделей на одном ключе:
```
[ Подключение ▾ ]  →  [ Модель ▾ ]   [⚡лимит]  [Проверить]
   (baseUrl+ключ)       (из /models     (бейдж     (пинг +
                         или вручную)             латентность))
```
- Селект **фильтрует по capability**: в «графику» попадают только записи `kind: image`,
  в «код/текст» — `kind: llm`. Одно и то же подключение может давать и то, и другое.
- «Добавить подключение» — форма: имя, baseUrl, протокол, ключ (env-имя или поле),
  «подтянуть модели» (`GET /models`) или вписать вручную.
- Реестр произвольной длины, лимита 1–2 модели нет; в каждом селекте активна ровно одна,
  остальные — кандидаты (цепочка fallback прячется под «дополнительно», по умолчанию выкл.).

### Противоречия, которые два селекта создают, и как решаем
1. **Vision (зрение на скриншоты) — это не «графика» и не «текст».**
   Проверка результата — модель *смотрит* скриншот. Это свойство LLM-селекта, а не график
   (`kind: image` картинки только создаёт, не читает).
   → Решение: у моделей `kind: llm` флаг `vision: true|false`. Визуальная проверка
   использует **ту же модель из «кода/текста»**, если у неё `vision: true`;
   если `false` — проверки сводятся к детекторам (console/overflow/anchors),
   в отчёт пишется «vision недоступен». Третьим видимым селектом не делаем.
2. **Код и тексты были разными ролями, а селект один.**
   → Одна выбранная модель, но **разные параметры на роль** (темп, макс. токенов,
   «пиши только CSS-патч»). Роль ≠ модель: роль — набор параметров + шаблон промпта.
3. **Один генератор картинок на всё**: hero-фото и плоские иконки/иллюстрации часто требуют
   разных моделей.
   → MVP один; в схеме заранее поле `roles.image.override` (например, «иконки — другая модель»),
   в UI появляется как «дополнительно», а не как обязательный селект.
4. **Счётчик лимита у чего — у модели или у подключения?**
   → У **подключения** (один ключ = одна квота), в бейдже показывается остаток подключения;
   у модели в выпадающем — только оценка стоимости ($/1M или $/картинка).
   Иначе две модели с одного ключа покажут два «остатка», которые на самом деле один.
5. **«Графика» ≠ только растр**: SVG/иконки не генерятся кидай-моделью.
   → В селект графики можно выбрать `none` = «без растровых изображений» (только HTML/CSS/SVG).
   Для прелендов это честный рабочий режим, а не деградация.
6. **Неизвестный протокол у подключения** (у kie.ai задача+опрос, у OpenRouter chat).
   → У подключения поле `protocol`: `openai-chat` | `task-poll` | `custom`;
   раннер работает с «задачей со статусом», протокол — лишь адаптер (раунд 5).

### Риски плана «только API-модели, imagening вне списка»
- Пока нет kie.ai-ключа, генератор картинок ровно один → его простой/кончился лимит
  валит прогон. → Нужен **второй fallback и ручная загрузка**: кнопка «подложить свои фото»
  в проект, оркестратор ставит их вместо сгенерированных и помечает в отчёте.
- ❓ Сделать ли такую ручную загрузкуImages штатным режимом «без генерации» (для отладки
  промптов текстов/кода без расхода на картинки)? Дефолт: да, режим `images: none | api | manual`.

## Раунд 8 — vision зашиваем, лимит-счётчик, устойчивость картинок
### Vision: пользователь его не выбирает вообще
- Правило: **vision = свойство модели, а не настройка юзера.** В UI нет ни селекта,
  ни чекбокса «vision».
- Способность определяется **один раз при проверке подключения**: кнопка «Проверить»
  (и мастер первого запуска) шлёт тестовый запрос «маленький png + «что на картинке?»».
  Прошёл → `vision: true` в реестр (кэшируется, сброс по кнопке «Проверить»).
- Выбор модели для зрения — **детерминированный алгоритм**, не решение человека:
  1) если активная модель селекта «код/текст» имеет `vision: true` — она;
  2) иначе — первая enabled-модель того же селекта с `vision: true` (по приоритету в реестре);
  3) иначе — зрение выключено, в отчёт строка «vision недоступен: нет ни одной
  vision-модели, тесты только детекторами» + подсказка, как починить.
- Прогон не стартует без vision **предупреждением**, не блокировкой (иначе нельзя
  отлаживать тексты дешёвой моделью). Флаг `requireVision` в settings.json по умолчанию true
  = предупреждение; юзер один раз сказал «ок» — не пилить каждые 5 минут.
- Цена вопроса известна заранее: перед прогоном в смете пишется «N скриншотов × vision».

### Счётчик лимита: оптимальная схема
- **Счётчик всегда у подключения** (ключ = квота). Модель его не имеет, у неё в списке
  только **цена** ($/1M токенов, $/картинка) — это свойство модели, не квоты.
- Формат бейджа на строке подключения:
  `⚡ 62% · ≈$3.10` (провайдер отдаёт кредиты) / `⚡ 3 200 / 10 000` (единицы API)
  / `∞` (безлимит вручную) / `?` (неизвестно) / `⛔ 0` (исчерпан → авто-исключение из ролей).
- Обновление событийное, не поллингом: при открытии UI, после каждого прогона, по клику
  на бейдж. Таймстамп «обновлено 12 мин назад» мелким шрифтом — чтобы цифра не врала молча.
- Жёлтый <20%, красный <5% или 0. При 0: роль откатывается на fallback-подключение,
  прогон продолжается, в отчёт — запись «лимит X исчерпан в середине прогона».
- Подсчёт «своего расхода» локальный и отдельный: за прогон и за месяц (run.jsonl),
  показывается в тултипе бейджа рядом с остатком провайдера — «потрачено: 142k токенов ≈ $0.05».

### Картинки: единственный генератор не должен валить прогон
Иерархия спасения (каждый уровень пишет явную запись в defects/отчёт):
  1. повтор с варьированием промпта ×2;
  2. следующее enabled image-подключение в приоритете реестра (цепочка, по умолчанию выкл.);
  3. **SVG-плейсхолдер в палитре проекта** по именам из site-plan.json — страница
     собирается, тестируется и выглядит «временно-чисто», а не сломанно;
  4. только если картинок нет в принципе и юзер не выбрал `images: none/manual` —
     прогон в `needs_human`, не в «fail».
- Ключевая свобода даёт site-plan.json: имена картинок зафиксированы до кода ⇒
  **пост-операция «догенерить картинки»** — пере-генер failed-список в те же имена,
  без переписывания HTML и без нового расхода на LLM. Кнопка в карточке прогона.
- Режимы селекта графики: `api (подключение) | none (чистый CSS/SVG) | manual (свои фото)` —
  manual = штатный режим с первого дня: вкладка загрузки, файлы кладутся в assets/img
  по именам плана, недостающие — плейсхолдер. Дёшево отлаживать промпты кода/текстов.

## Раунд 9 — оркестрация: кто управляет запросами
### Слои (один Node-процесс, никаких Redis/BullMQ — иначе «передать коллеге» ломается)
```
UI (React)
  │ SSE событий + REST команд
  ▼
RunManager        — один инстанс на прогон; живёт, пока прогон активен; убиваем по AbortSignal
  ▼
Scheduler (DAG)   — знает граф задач, лимиты дорожек, шлюзы(gates), цикл фиксов
  ▼
Runners           — llm-runner · image-runner · browser-runner · fs-runner
  ▼
Connections       — единственное место, где бывает сеть (baseUrl+ключ+протокол+квота)
```
Правила:
- **Runner — единственный, кто умеет «делать» шаблон/файл/скриншот.** Оркестратор не знает
  ни про OpenRouter, ни про kie.ai — он знает «задача task-copy нужна, задача image-3 не готова».
- **Connections — единственный, кто ходит в сеть**: резолвит ключ, ставит заголовок,
  считает usage в run.jsonl, дёргает счётчик лимита, ретраит транспортные ошибки.
  Провалидировать подключение может и UI напрямую, но рабочие запросы — только через него.
- Оркестратор **не хранит «правду» в памяти**: источник истины = события в `run.jsonl`
  + артефакты на диске. Упал процесс → при старте прогон восстанавливается: задача
  считается готовой, если артефакт есть и его хэш (вход+промпт+модель+version) совпал.

### Граф (декларативно, общий для White/Black, различия в параметрах и шлюзах)
```
brief → expand? → plan → ⛔gate(plan) ─┬→ copy ──────────────────┐
                                       ├→ image-prompts → imgs[N] ─┼→ assemble → shoot → judge ─┐
                                       └→ palette/fonts ──────────┘                             │
                      ┌──────────────────────────────────────────────────────────────────────────┤
                      ▼                                                                           
                 fix (≤ maxFixRounds, только CSS/HTML-патч) → shoot → judge ──→ export → report
```
- Цикл fix — условное ребро со счётчиком, не рекурсия функций.
- Картинки стартуют **сразу после плана**, не дожидаясь кода: ветки copy/images/code параллельны.
- `assemble` не ждёт «всё подряд», а ждёт три конкретные зависимости: copy, код, карту
  картинок (плейсхолдер = валидный результат, ветка не блокируется).

### Дорожки параллелизма (семафоры в планировщике, значения в settings.json)
```
lanes: { llm: 2, image: 4, browser: 1 }   # browser=1 жёстко: 7.8 ГБ RAM
```
- Лимит не «на весь прогон», а на **тип ресурса**: 4 картинки + 2 LLM-запроса одновременно
  — это нормально; второй Chrome — нет.
- Очередь одна, приоритет: критический путь (plan→code→assemble) выше, чем
  «догенерить картинку №7».

### Классы ошибок → четыре разных реакции (а не «всё retry»)
| класс | пример | реакция |
|---|---|---|
| transport | 500/502/timeout | ретрай с экспоненциальной задержкой ×3, тот же промпт (кэш не трогает) |
| contract | HTML без фенсов, битый JSON плана, имена файлов не из плана | **не** ретрай вслепую: повтор с приложенным текстом ошибки (самокоррекция 1 раз), дальше — стоп |
| quota | 429/квота=0 | падение на fallback-подключение; нет fallback — пауза прогона, а не fail |
| fatal | нет ключа, Chrome не поднялся | прогон в needs_human с человеческой строкой |

### Команды из UI (REST на RunManager)
start · pause · resume · cancel(abort всё, у внешних задач cancel) · skip(gate) ·
retry(task) · regenerate-images(failed) · fork(variant).
Каждая команда = событие в тот же `run.jsonl` (и история прогона = журнал аудита бесплатно).

### Что НЕ берём (дорого, локале не нужно)
Redis, worker-пул вне процесса, cron, распределённые lock'и, «очередь на сервере».
Многопользовательский сервер в будущем = «запустить ещё один сайдкар на другую папку»,
а не переписывать оркестратора.

## Раунд 10 — шлюз после плана принят (дефолт), требования к нему
- ✅ Единственный шлюз по умолчанию — сразу после `plan`. Дальше прогон автономен
  до отчёта. Остальные шлюзы (copy, images) — опция «для перфекционистов», выкл.
- Что такое gate для юзера, три экрана-секунды:
  1. **Карточка плана** (не JSON!): список секций карточками (тип, заголовок-H2, slug),
     палитра плашками, список картинок «slug → что будет на картинке», смета
     «N картинок · ~X токенов · ориентировочно $Y».
  2. Действия в один клик: **[Поехали]** (главная, горячая Enter) ·
     [Править] (тот же редактор: перетащить секцию, выключить, переименовать slug,
     сменить hex; картинкам — правка промпта-описания) ·
     [Перегенерить план] (с комментарием: «убери pricing, добавь FAQ» — правка, а не лотерея)
     · [JSON ▾] для тех, кто хочет доверие через исходник, не через карточку.
  3. Всё изменённое помечается точкой; «Поехали» применяет правки как новый план
     (пересчитывается хэш → картинная ветка не возьмёт устаревшие имена).
- Скорость как требование: план генерится copy-моделью за 10–20 с, таймер на карточке
  шлюза; UI не блокируется — поля брифа остаются видны (свернутый аккордеон).
- После «Поехали» шлюза больше нет: все артефакты копятся в правой панели,
  юзер может уйти; прервать можно кнопкой в любой момент.
- Память настройки: если юзер 3 раза подряд жмёт «Поехали» не правя план — предложить
  («не показывать снова?») автостарт с отменой в первые 3 секунды (undo-стиль тоста).
